# Один сервер: установка, диагностика и обновление

Комплект рассчитан на Linux с systemd и уже работающими локальным MTProxy и TLS frontend. Он устанавливает только relay; домен, сертификаты и MTProxy остаются под вашим управлением. Для обычной работы Python не нужен; команда `doctor` использует Python 3 со стандартной библиотекой. Новых постоянно работающих компонентов нет.

## Первая установка

1. Соберите Linux-бинарник для архитектуры сервера: `cargo build --release --locked -p qdynn-server`. macOS-бинарник для этого не подходит.
2. Скопируйте `deploy/config.minimal.toml` за пределы репозитория, задайте свой домен и **существующий секрет MTProxy**, ограничьте права файла до `0600`. Поместите свой статический сайт с `index.html` в `/var/www/qdynn`; каталоги должны быть доступны пользователю `qdynn` на чтение/проход. Секрет и конфигурацию не кладите в `public_dir`.
3. Выполните:

```sh
./target/release/qdynn-bridge check-config --config-file /absolute/path/config.toml
sudo bash deploy/manage.sh install ./target/release/qdynn-bridge /absolute/path/config.toml
```

Скрипт создаёт системного пользователя `qdynn`, `/etc/qdynn/config.toml` (`root:qdynn`, `0640`), бинарник `/usr/local/bin/qdynn-bridge` и службу. Уже существующие бинарник/config/unit не перезаписываются: действующую нестандартную установку сначала нужно вручную сопоставить с этими путями. Служба перезапускается при аварии, имеет лимит 65536 FD и доступ к файловой системе только на чтение. Размещайте сайт вне `/root` и `/home`, которые служба не видит.

4. Сопоставьте `nginx.conf.example` с вашей конфигурацией Nginx: замените hostname и пути сертификатов, сохраните собственный ACME renewal. Шаблон предназначен для `http {}` и обычного TLS virtual host; существующий SNI/stream ingress требует отдельной интеграции. Скрипт не изменяет Nginx и не выпускает сертификаты. После ручного включения проверьте `nginx -t`, затем выполните graceful reload.
5. Запустите:

```sh
sudo /usr/local/bin/qdynn-bridge doctor --config-file /etc/qdynn/config.toml
sudo /usr/local/bin/qdynn-bridge --config-file /etc/qdynn/config.toml --print-link
```

`doctor` проверяет backend TCP, DNS/TLS/HTTPS, bridge CSP/no-store, HELLO/WELCOME и WS Upgrade для настроенного carrier. Для `auto` проверяются HTTPS и WS отдельно. Диагностика создаёт временные сессии и пытается удалить их в `finally`; при обрыве они удаляются сервером по TTL. Credentials передаются диагностике через stdin, не печатаются и не передаются в argv. Deadline всей диагностики — 90 секунд; ненулевой exit code означает найденную проблему. TLS certificate verification обязательна, redirects не выполняются. Это проверка пути от сервера до своего публичного домена; Android, операторский DPI, MTProto и настоящая передача пользовательских сообщений проверяются отдельно.

`--print-link` намеренно печатает секрет в ссылке/QR; не отправляйте его вывод в общие журналы.

## Выбор транспорта

Минимальный конфиг сохраняет совместимый `websocket`. После проверки целевой Android/WebView сборки можно поставить `carrier_mode = "auto"`: WS → HTTPS при стартовом отказе, а также при неудачном WS opening во время восстановления. Сначала выполняется одна WS-попытка восстановления; HTTPS fallback использует остаток того же startup budget. После перехода bridge остаётся на HTTPS до нового запуска. Auth/protocol failures не запускают перебор carrier. Настроек резервных доменов и обучения нет.

## Обновление и откат

```sh
sudo bash deploy/manage.sh update /absolute/path/new/qdynn-bridge
sudo bash deploy/manage.sh rollback
```

Кандидат проверяется командой `check-config` с **текущим** конфигом, без унаследованных `QDYNN_*` переопределений. Затем бинарник заменяется через rename в том же каталоге, предыдущий сохраняется как `qdynn-bridge.previous`. Config и unit не изменяются. После рестарта проверяется состояние службы; при неудаче старый бинарник возвращается автоматически. Это проверка запуска процесса, не backend/MTProto: после обновления повторите `doctor`. Перезапуск разрывает активные сессии.

`rollback` меняет местами текущий и предыдущий бинарники после проверки совместимости предыдущего с текущим config. Скрипт не откатывает ручные изменения config. Операции защищены lock-каталогом; после SIGKILL остаточный lock удаляется вручную только после проверки отсутствия другого обновления.

Для проверки файлов без запуска служб задайте абсолютный временный каталог:

```sh
QDYNN_ROOT=/absolute/temporary/stage bash deploy/manage.sh install /absolute/path/binary /absolute/path/config.toml
```

Этот режим не создаёт пользователей, не запускает systemd и не меняет Nginx; кандидат должен быть исполняемым на локальной ОС. Пути внутри unit сохраняются production-путями.
